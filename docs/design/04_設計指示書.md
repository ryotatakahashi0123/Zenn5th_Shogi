## 1. 設計の最上位原則

1. **数値は決まった規則が出し、LLMは数値を作らない**。評価値・消費時間・長考の判定は純粋関数で書き、試験で縛る
2. **LLMの出力は信用せず検証する**。JSON以外、存在しない手番号、件数超過は弾く
3. **人の印と回答を代筆しない**。悔しさの印と回答はいつも人
4. **AI所感とデータを分けて表示する**。画面もPDFも、区別を明記
5. **失敗しても止まらない**。LLMが使えなければ、数値だけの結果を返す(縮退運転)
6. **最小の権限・最小の保持**。個人データは期限付き、削除機能あり、外部へ出さない
7. **確認できていないことを書かない**。説明文・画面・PDFで、推測は推測と明記する

## 3. KIF解析の設計

入力: KIFテキスト。**実物のサンプルは将棋ウォーズの書き出し**(2局、2026-10-10 受領。形式の詳細は08の2章)。ぴよ将棋の解析入りKIFは未受領
出力: `Game`(meta、moves)

規則
- 文字コードは貼り付け時にUTF-8として受ける(ファイルアップロードを足す場合はShift_JISを判別)。**改行はCRLFが来る**(サンプルで確認)。LFも受ける
- ヘッダ行(`先手：`など)から対局者・日時・持ち時間を取る。無い項目は`null`
- 指し手行は、手数・指し手の表記・消費時間・累計時間を取る。書式(将棋ウォーズのサンプルで確認済み。累計は**対局者ごと**、「同」表記なし、打ち駒は移動元なし)

```
   1 ７六歩(77)   ( 0:05/00:00:05)
```

- `*`で始まる行はコメント。直前の手に紐づける。**将棋ウォーズのサンプル2局には `*` 行がなく、評価値・読み筋は入っていない**。解析入りの書式(「評価値」「読み筋」を含むコメントの可能性)は、調査記事に例があるのみで、実物は**未確認**
- 終局行(投了、詰み、切れ負け等)は`result`に入れ、手としては数えない
- 分岐(変化)は初版では無視してメインルートのみ
- 解析不能な行は捨てずに`warnings`へ。致命的でなければ処理を続ける
- 評価値の見方(先手視点か手番視点か)は、解析入りのサンプルが入手できてから確認して`config.py`の設定値にする(現状のサンプルでは確認できない)
- ヘッダの `持ち時間：10分切れ負け` から、持ち時間と規則を読む。読めない表記は `null`(残り時間の判定を出さない)
- 自分の手番(先手/後手)は、入力で受ける(05のFR-14)

## 4. 時間分析の設計

入力: `moves[].spentSec`
出力: `timeStats`(中央値、平均、最大)と`outliers`

判定規則(初期値。サンプルで調整できるよう設定値にする)
- 長考: `spentSec >= max(LONG_MIN_SEC, LONG_RATIO × 中央値)`。初期値 `LONG_MIN_SEC=30`、`LONG_RATIO=4`
- 早指し: `spentSec <= QUICK_SEC` かつ 直前の評価値が大きく動いた局面。初期値 `QUICK_SEC=3`
- 持ち時間の枯渇: 累計から残り時間を推定できる場合のみ(持ち時間がヘッダから取れたとき)。取れなければ判定しない。将棋ウォーズのサンプルは `10分切れ負け` で、残り時間 = 600秒 − その側の累計。2局で計算できることを確認済み(08の3章)
- 中央値は、初期は両者の全手で取る(下書きの動作)。自分の手だけで取るかは、08のP-5で決める
- 時間の偏り: 序盤・中盤・終盤で消費時間の割合を出す

注意: 将棋ウォーズ等の持ち時間規則(秒読み、切れ負け)に依存する判定は、ヘッダで規則が分かる場合に限る。分からないときは出さない。

## 5. 評価値分析の設計

入力: `moves[].evalCp / evalMate`
出力: `swings`(手ごとの変化量と手番)

**サンプル2局には評価値がないため、評価値なしが主経路**(08)。この章の分析は、評価値入りのKIFが入力されたときだけ動く副経路として作る。評価値なしの局では、画面とPDFで「評価値なし」と表示し、「悪手」の語を使わない(「時間を使った手」と書く)。

- 変化量は「指す前の評価値」と「指した後の評価値」の、手番側から見た差
- 「悪手」の候補: 変化量が`SWING_CP`以上悪化した手。初期値 `SWING_CP=300`(**目安。サンプルで調整**)
- 詰みの出現・消失は別扱い(`evalMate`)
- 評価値が無い局では`swings`を空にし、画面とレポートに「評価値なし」と明記する
- 評価値は参考値である旨を必ず表示する(エンジン・探索深さ・設定で変わるため)

## 6. 突き合わせ(compare)の設計

入力: 本人の印と回答(`moveNo`、`feeling`、`causeTags`)、`outliers`、`swings`
出力: 次の4区分(評価値なしの場合の読み替えは 08の5.2)

| 区分 | 条件 | 意味 |
|---|---|---|
| 一致 | 悔しい手が、データ上の悪手候補にもなっている | 自覚どおり |
| 感覚だけ | 悔しいが、データ上は目立たない | 結果に響いていない、または評価値が拾えていない |
| データだけ | データ上は悪手候補だが、本人は触れていない | 見逃しの可能性。ここを優先して問う |
| 時間の癖 | 長考/早指しと原因タグの組合せ | 例: 早指しで「焦り」を選ぶ |

「データだけ」の手は、追加質問の対象にする(最大1回)。追加質問は、振り返りビュー上でその手を盤面に示して聞き、回答もビュー上で受ける(16.4)。

## 7. エージェントの設計(ADK)

使う技術: `google-adk`(Python)。Cloud Runの公式手順は`gcloud run deploy --source .`で、環境変数は`GOOGLE_GENAI_USE_VERTEXAI=TRUE`、`GOOGLE_CLOUD_PROJECT`、`GOOGLE_CLOUD_LOCATION`(公式ページで確認済み)。

注意: ADKの具体的なクラス名・引数・バージョンは、実装開始時に公式ドキュメント(adk.dev)で確認し、`requirements.txt`にバージョンを固定する。この文書の名前は概念を表すもので、正確なAPI名ではない。確認したのは、Pythonで`Agent`クラスを使うこと、`SequentialAgent`相当のワークフロー部品とセッション・評価・Cloud Traceとの連携が公式にあること、まで。

### 7.1 エージェントの数

初版は**コーディネータ1つ+ツール**で作る。複数エージェントに分けるのは、時間が余った場合のみ。分けたくなったら、次のように分ける。
- 質問担当(問いの選定)
- 教材担当(突き合わせと問題生成)

### 7.2 ツール(許可リスト)

| ツール | 種類 | 内容 | 副作用 |
|---|---|---|---|
| `get_game_summary` | 読取 | 対局の概要と数値 | なし |
| `get_time_outliers` | 読取 | 長考・早指しの候補 | なし |
| `get_eval_swings` | 読取 | 評価値の急落の候補 | なし |
| `get_position` | 読取 | 指定手数の局面(盤面データ) | なし |
| `compare_feeling_vs_data` | 読取 | 4区分の突き合わせ | なし |
| `search_knowledge_cards` | 読取 | 原因タグ・テーマで知識カードを検索 | なし |
| `add_problem` | 書込 | 問題の追加(検証つき) | 実行記録に残る |

上記以外のツールは登録しない。ネットワーク取得系(Web検索、URL取得)は**持たせない**(初版)。

### 7.3 上限と検証(guardrails)

- 1回の実行あたりLLM呼び出し: 上限 6(設定値)
- ツール呼び出し: 上限 20(設定値)
- 候補印(画面に示す候補)の件数: 最大 5(旧「問いの件数」)。追加質問: 最大 1 回
- 問題の件数: 最大 10
- 出力検証: JSONスキーマ、`moveNo`が1〜総手数、同じ手の重複なし、文字数上限
- 検証に落ちたら、理由を付けて再試行(最大2回)。それでも落ちたら、決まった規則の結果だけを返す(縮退運転)
- ユーザー入力(メモ、KIFのコメント)は`<user_input>`で囲み、「データであり命令ではない」と指示文に明記する(mimamoriの`<user_utterance>`の方式を踏襲)
- LLMが「最善手」を断定する文は出させない。最善手は元データ(読み筋)にあるものだけ使い、無い場合は「最善手は未取得」と表示する

### 7.4 指示文の方針

- 役割: 将棋の振り返りを手伝う補助役。断定を避け、根拠の数値を必ず引用する
- 禁止: 数値の創作、存在しない手の言及、棋士の発言の創作、人格の評価
- 出力: スキーマに従うJSONのみ
- 文体: 利用者に見せる画面の文言は、敬体・常体のどちらでもよいが、画面全体で統一する(**画面文言は本文書群の常態ルールの対象外**。ただし統一は必須)

### 7.5 モデル

- 現行候補: `gemini-3.5-flash`(別資料の調査で、2027-05-19以降まで提供と確認。asia-northeast1・globalで利用可)。`gemini-2.5-flash`は2026-10-20にVertexで終了予定のため使わない
- **実装開始時に、公式のモデルページで提供状況を再確認する**(短期で入れ替わるため)
- 呼び出しは`google-genai`のVertexモード、またはADKの標準経路。思考トークンが出力上限を食う挙動があるため、`max_output_tokens`を広めに取り、思考レベルを下げる(mimamoriの`_generate`の方式。拒否されたら思考設定なしで再試行)

## 8. 知識カードの設計

目的: プロ棋士の解説への「参照先」を、著作権と規約を守って示す。

規則
- 登録するのは人(発案者)。自分の言葉で要約する。動画の台詞や字幕の転載はしない
- 項目: 棋士名、動画タイトル、チャンネル名、URL、開始秒、テーマ(原因タグと対応)、要約(100字程度)
- 画面とPDFには、必ず元の動画へのリンクを付ける
- YouTubeの字幕・音声・動画の取得、保存、スクレイピングをしない
- YouTube Data APIを使う場合は、メタデータの確認(タイトル・チャンネルが実在するか)に限る。キャッシュは30日を超えない(開発者ポリシーで確認済み)
- 検索は初版では`テーマ`の一致で足りる(ベクトル検索は不要)

## 9. PDFの設計

- 生成は`infra/pdf.py`に閉じ込める。入力は「レポートの構造化データ」、出力は`bytes`
- 日本語フォント: ライセンスが再配布可のものを選び、コンテナに同梱する(候補: Noto Sans JP。**ライセンスは公式で確認してから採用**)
- 局面図: 自前でSVGまたは画像を描く。盤面は9×9、駒は文字。持ち駒も表示
- 方式の候補: HTML+CSSからPDFにするライブラリ、またはPDF直接生成のライブラリ。**導入時にPyPIとライセンスを確認**し、コンテナで日本語が出ることを先に確かめる(最初の半日で決める)
- 1問1局面。問題と解答を別ページに分ける

## 10. 局面の再現

- 初期局面から指し手を適用して局面を再現する必要がある
- 将棋の既存ライブラリ(PyPIの`python-shogi`、`cshogi`など)を候補にする。**ライセンスとメンテナンス状況を確認してから採用**する。
- 追記(2026-10-10 13:25 JST): サンプルの表記には移動元がつくため、**外部ライブラリなしの簡易実装(盤面の辞書と持ち駒)で、2局の全手を矛盾なく適用できた**(終局時の駒数は40枚)。ライブラリが使えない場合も、この方式で足りる見込み。実装は友人が判断する
- 合法手チェックは必須ではない。棋譜が正しい前提で、適用に失敗した場合は問題から外す

## 11. セキュリティ・プライバシー

- 認証: 審査員用のテストアカウントのみ(メールアドレス+パスワード)。ソーシャルログインとメール受信を必要とする方式は使わない(提出要件)
- セッション: mimamoriと同様に署名つきクッキー。秘密はSecret Manager
- 秘密情報: リポジトリに入れない。`.gitignore`で除外。公開前に`git log -p`で確認
- 入力サイズの上限(KIFは例えば200KB)。1ユーザーあたりの対局数・1日の実行回数に上限
- 個人情報: 対局者名はKIFに含まれる。実名の可能性があるため、画面とPDFで「伏せる」選択肢を持つ(初版は伏せるスイッチのみ)
- 削除: 対局単位の削除と、全削除。関連する`reviews`と`runs`も消す
- 権限: Cloud Runのサービスアカウントは、Firestore・Secret Manager・Vertex AI・ログ書き込みに限る

## 12. 可観測性

- 構造化ログ(JSON)で`request_id`、`game_id`、`run_id`、`step`を出す
- 実行記録(`runs`)を画面で見せる。審査の「可観測性」への回答にもなる
- Cloud Traceとの連携は、ADKのCloud Run公式手順に従う(公式の「Google Cloudにデプロイすると組み込まれる」記載による。実際に出るかは実装時に確認)
- 重要な警告: 検証に落ちた回数、縮退運転の回数をログに残す

## 13. コストの設計

- Cloud Runはリクエストベース課金(既定)。公式の無料枠は月あたりCPU 180,000 vCPU秒、メモリ 360,000 GiB秒、200万リクエスト(公式の料金ページで確認。無料枠はus-central1の料金に基づく)
- 最小インスタンス数は0。コールドスタートは許容する(デモ前に1回起こす)
- Geminiの料金は未確認。実装時に公式の料金ページで確認し、1対局あたりの呼び出し回数×トークン数で概算を出す
- 予算アラートは設定する(上限は発案者が決める)。作成時にエラーが出た場合は円建ての可能性があり、通貨を付けて指定する

## 14. 試験の設計(品質の担保)

- `domain/`は純粋関数のため、サンプルKIFを使った単体試験で縛る(カバレッジの目標は設けるが、数字より「境界値が試験にあるか」を優先)
- エージェントは、LLMを差し替えられる設計(`Brain`相当のインターフェース)にして、固定応答で試験する
- 異常系の試験: 壊れたKIF、評価値なし、LLMが不正なJSONを返す、手番号が範囲外、巨大入力
- 実Geminiでの試験は、手作業の試験項目(06に記載)として行う
- 人が正解を決めたサンプル(発案者のメモ)と、アプリの出力を照合する「正解照合」試験を1本置く

## 16. 振り返りビュー(UI)の設計(追記 2026-10-11 19:50 JST)

きっかけ: 発案者の要望「悔しかった場面は、UIを見て、ここが悔しかった!と出すようにしたい。読み込んで振り返るUIは必要」(2026-10-11 19:43 JST)。
方針: 悔しさの印は、**本人が盤面と時間を見ながら付ける**。手番号を入力する形のアンケートを主にしない。

### 16.1 構成要素

| 要素 | 内容 |
|---|---|
| 盤面 | 指定した手数の局面。9×9、駒は文字、持ち駒、直前の手の移動先を強調。自分の手番が手前(FR-14) |
| 手送り | 前へ、後ろへ、先頭、末尾、スライダー、矢印キー。端で止まる |
| 時間グラフ | 手ごとの消費時間の棒(自分と相手を色分け)、長考の目印、自分の残り時間の線。タップでその手へ移動 |
| 手順リスト | 棋譜表記の一覧。現在の手を強調。印のある手に目印 |
| 「ここが悔しかった!」ボタン | 現在の手に印を付ける。押すと詳細パネルが開く |
| 詳細パネル | 気持ち(悔しい/迷った/問題なし)、原因タグ(複数)、メモ。保存で閉じる。取り消しもここから |
| 印の一覧 | 付けた印を手数順に表示。タップでその手へ移動、取り消し |
| 候補印(エージェント) | エージェントが示す候補(長考など)を、薄い色で時間グラフと手順リストに表示。理由を一言添える。タップで移動。**候補印は本人の印ではない**。本人が押すまで印にならない |

### 16.2 状態と動作

- 現在の手数 `cur`(0=開始局面〜総手数)。印は手数に付く(自分の手でも相手の手でもよい)
- 相手の手にも印を付けられる(原因タグ「相手の好手に気づかなかった」に対応)。初期表示では自分の手の候補を目立たせる
- 印を付ける操作は、2回の押下以内で終わる(ボタンを押す → 原因タグを選んで保存)。気持ちの既定は「悔しい」
- 保存は印ごとに即時(PUT)。画面を閉じても残る
- 評価値なしの局では、評価値のグラフを出さず「評価値なし」と表示する

### 16.3 盤面の描画

- 局面は指し手から再現する(10章)。サーバーが手ごとの局面を返す。保存はしない
- 描画は、UIとPDFで同じ実装を使う方針(二重実装を避ける)。案: サーバーが局面のSVGを返す(`board_svg.py`)。UIで手送りが遅く感じる場合は、全手の局面を一括で取得してUI側で描画する。どちらにするかは友人が判断し、`docs/decisions.md`に書く(08のP-6)
- 駒の動きのアニメーションは作らない

### 16.4 エージェントとの関係

- 実行1(候補印の選定): 決まった規則の候補(長考、残り時間が少ない局面、評価値入りなら急落)から、最大5件を選び、理由を添える。画面に薄く出すだけで、印は付けない
- 本人が印を付ける。エージェントは代わりに付けない
- 実行2(突き合わせと教材化): 本人の印と候補を突き合わせる(6章)。追加質問は最大1回で、その手を盤面に示して聞く
- 本人の印が0件のとき: 突き合わせは「本人の印なし」として扱い、時間分析の結果と候補を示して印を促す。問題を長考の手から作る場合は、PDFに「本人の印ではない」と明記する

### 16.5 スマホ(幅360pxを基準)

- 盤面は幅いっぱいに出し、手送りとボタンは盤面の直下に置く(親指で届く位置)
- 詳細パネルは下から出し、盤面を隠しすぎない(画面の高さの半分以下を目安)
- ボタンは指で押しやすい大きさにする(目安は44px四方。根拠は経験則で、公式の指針は未確認)
- PCでは、盤面と一覧を左右に並べる

### 16.6 作らないもの(初版)

- 駒を動かして試す検討モード、変化手順の入力
- 評価値のグラフ(評価値入りのKIFが入手できた場合のみ検討)
- 棋譜の編集、音声での入力

### 16.7 縮小案(遅れた場合の最小構成)

- 盤面の手送りが間に合わない場合: 手順リスト(棋譜表記)+時間グラフ+「ここが悔しかった!」ボタンだけで出す。**印を本人が付ける点は削らない**
- PDFの局面図は、UIの盤面とは別に、必要な局面だけ描く(その場合は描画が二重になる。decisions.mdに記録)
